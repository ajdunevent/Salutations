# Developing Salutations

Building, packaging and the technical notes behind Salutations. For what
the app does, see the [README](README.md).

Salutations is a GTK4/libadwaita app in Rust. Accounts come from GNOME
Online Accounts; mail goes through Evolution Data Server's Camel library.
It is IMAP and SMTP only, with one folder tree per account and no unified
inbox.

## Layout

| Path | What it is |
| --- | --- |
| `bindings/camel-sys`, `bindings/edataserver-sys` | FFI crates generated by gir from `Camel-1.2` and `EDataServer-1.2` |
| `bindings/camel`, `bindings/edataserver` | Safe wrappers: generated `src/auto/`, hand-written everything else, including `CamelSession` subclassing |
| `salutations-core` | GTK-free mail engine: session, GOA account discovery, credentials, certificate trust, message rendering, link and tracking checks, sender verification, avatars, the remote content cache, offline sync, settings |
| `salutations` | The GTK4/libadwaita app |
| `gir-files` | GIR inputs: gtk-rs's GLib/GObject/Gio, and Fedora 44's EDS 3.60 files patched by `scripts/fix-girs.py` |
| `scripts` | Binding regeneration, Flatpak crate list, development builds |
| `build-aux` | Flatpak manifest and its crate list |
| `salutations/data` | Desktop file, AppStream metainfo (also read by the About dialog), icons, stylesheet |
| `screenshots` | Store screenshots, referenced from the metainfo by their URLs on the `main` branch |

## Building and running

EDS 3.56 is the minimum. Camel's C API changed in 3.58 (libcamel is
.so.64 in 3.56, .so.67 in 3.60). The bindings are generated from 3.60
with 3.56 as the oldest version, so the generated API added since then
is behind the `v3_58` and `v3_60` features, which Salutations does not
use. The few calls it needs whose API changed are in
`bindings/camel/src/compat.rs`, and the `camel` crate's build script
picks the 3.56 or 3.58 form from the installed Camel version.

Builds happen in a Fedora toolbox Distrobox of the same release as the
host, so the binary runs on either. The host needs GNOME Online Accounts
and `evolution-source-registry`, which Silverblue ships, and at least
one account in Settings > Online Accounts with Mail switched on.

Inside the container:

```sh
sudo dnf install evolution-data-server-devel gtk4-devel libadwaita-devel \
    webkitgtk6.0-devel gtksourceview5-devel libspelling-devel gcc \
    pkgconf-pkg-config python3
cargo test -p camel-sys -p edataserver-sys
cargo build -p salutations
```

The binary links GtkSourceView 5 and libspelling (the composer's editor
and spell checking). The host needs both libraries to run it outside the
container; `ls /usr/lib64/libgtksourceview-5.so.0 /usr/lib64/libspelling-1.so.2`
shows whether it has them. Running it inside the container, or the
Flatpak, avoids that. Then, on the host:

```sh
~/Projects/Salutations/target/debug/salutations
```

On Debian forky and FuriOS (EDS 3.56):

```sh
sudo apt install libcamel1.2-dev libedataserver1.2-dev libebook1.2-dev \
    libgtk-4-dev libadwaita-1-dev libwebkitgtk-6.0-dev libsoup-3.0-dev \
    libgtksourceview-5-dev libspelling-1-dev pkgconf gcc rustc cargo
cargo build -p salutations
```

OpenPGP goes through Camel's GnuPG context, which runs `gpg` with the
user's keyring. The Flatpak reaches `~/.gnupg` but not the host's agent
sockets: gpg starts its own `gpg-agent` (and `keyboxd`, when the keyring
uses it) inside the sandbox from the GNOME runtime, as Evolution's and
Seahorse's Flatpaks do, so nothing has to be running on the host.
Passphrases come from the runtime's `pinentry-gnome3`, through GNOME's
system prompt; smartcards such as YubiKeys through `--socket=pcsc`.
A round trip against a throwaway keyring:
`cargo test -p salutations-core --test gpg -- --ignored`.

### Flatpak

`build-aux/net.dunevent.Salutations.json` builds Salutations on the GNOME
50 runtime together with what the runtime lacks: libical, the GNOME
Online Accounts client library, evolution-data-server 3.60.2 (Camel and
the client libraries; the sandboxed app uses the host's source registry
and address books over D-Bus) and libspelling. Crates come from `build-aux/cargo-sources.json`, so Cargo
builds offline; run `scripts/update-cargo-sources.sh` after any change to
`Cargo.lock`.

```sh
flatpak install flathub org.gnome.Sdk//50 org.gnome.Platform//50 \
    org.freedesktop.Sdk.Extension.rust-stable//25.08 org.flatpak.Builder
flatpak run org.flatpak.Builder --user --install --force-clean \
    build-dir build-aux/net.dunevent.Salutations.json
flatpak run net.dunevent.Salutations
```

The first build compiles evolution-data-server and takes a while; later
builds reuse it from `.flatpak-builder`. The Flatpak keeps its own
settings, caches and notification state in
`~/.var/app/net.dunevent.Salutations`, separate from a build run on the
host.

### Development builds for x86_64 and aarch64

`scripts/dev.sh`, run on the host, asks for the architecture (this
machine, the other one, or both), what to produce (a `.flatpak` file in
`dist/`, an install for the current user, or both) and the Cargo profile.
The bundled libraries are built once per architecture with
flatpak-builder and again only when the manifest changes; Salutations
itself is compiled with Cargo inside the SDK, so later runs rebuild only
changed code. State is kept in `.flatpak/`. Building for the other
architecture needs QEMU user emulation registered with binfmt_misc, and
its first run is slow because the bundled libraries compile under
emulation.

### Desktop file outside Flatpak

Notifications, the dock's unread badge and GNOME's per-app notification
settings find the app through its desktop file. Until there is a
package, install it with the path of the built binary:

```sh
sed "s|^Exec=salutations|Exec=$HOME/Projects/Salutations/target/debug/salutations|" \
    salutations/data/net.dunevent.Salutations.desktop \
    > ~/.local/share/applications/net.dunevent.Salutations.desktop
```

Remove that file when using the Flatpak: a desktop file in
`~/.local/share/applications` hides the one the Flatpak exports.

`SALUTATIONS_ANY_ACCOUNT=1` also lists IMAP accounts that do not come
from GOA. It exists for testing against hand-written EDS sources.
`SALUTATIONS_DEBUG=1` prints the time of each startup and sync step to
stderr; `CAMEL_DEBUG=imapx:io` adds the IMAP traffic.

The two test crates compare every struct layout and constant in the
bindings against the installed C headers. Run them after every EDS
update; a failure means the bindings need regenerating. They describe
EDS 3.60 and fail against older headers, whose structs differ; the app
reads none of the structs that differ.

Camel's state goes to `~/.local/share/salutations` and
`~/.cache/salutations`; deleting both resets it. The data directory also
holds each account's special folders, the messages allowed to load
remote content and those whose tracking removal was loosened; the cache
directory holds remote content and avatars. Preferences and
remote-content allow lists are in `~/.config/salutations/settings.ini`.

## Regenerating the bindings

When EDS changes or the ABI tests fail:

```sh
cargo install --git https://github.com/gtk-rs/gir \
    --rev f402b90c8ad678679e40011c008303b53f251619 gir
scripts/regen-bindings.sh
cargo test -p camel-sys -p edataserver-sys
```

The gir revision is the one gtk-rs-core 0.22.9 pins, matching the
`glib 0.22` crates. The script copies the system `.gir` files into
`gir-files/`, patches them and reruns gir on all four crates. A new EDS
release can need another case in `fix-girs.py`; the ABI tests show where.

## Findings

These shaped `salutations-core` and the app and apply to all later work.

- `camel_store_get_inbox_folder_sync()` opens "inbox" without going
  through the store's folder cache. The IMAPX server updates the cached
  folder, so the returned one never receives messages. It is left out of
  the bindings; `Session::inbox()` opens "INBOX" by name.
- No folder opens on a new account until the folder tree has been
  fetched once (`Session::folders()`).
- An offline store reports itself offline until Camel has checked that its
  host is reachable, and IMAPX refuses to connect meanwhile.
  `Session::connect_future()` runs the reachability check, then
  `camel_service_connect()`. It avoids `camel_offline_store_set_online()`
  where it can: going online opens every folder for offline sync, and
  IMAPX then sends a LIST per folder before the folder list is known.
- Camel connects an online store on any folder call, including a cached
  folder listing. The window takes the session offline while it shows
  the cached folder trees and INBOX at startup, then online to connect.
  The stores are created before that, while the session is online, so
  they can connect without the go-online step.
- `camel_store_get_folder_info()` on an online IMAPX store lists every
  folder on the server unless `FAST` is passed; `REFRESH` alone changes
  nothing.
- "Idle completed (N secs)" in the IMAP log is the time the connection
  spent idle, not a delay: Camel ends IDLE as soon as a command is queued.
- IMAPX settings default `filter-inbox` to true, so Camel asks the session
  for a mail filter driver on every new INBOX message. `CamelSession`
  has no default; the binding's `SessionImpl::filter_driver()` returns
  none.
- EDS 3.58 removed `camel_folder_get_uids()`, `camel_folder_free_uids()`,
  `camel_folder_search_by_expression()`, `camel_object_state_write()`
  and the boxed `CamelFolderThread`, and replaced them with
  `camel_folder_dup_uids()`, `camel_folder_search_sync()`,
  `camel_folder_save_state()` and a `CamelFolderThread` GObject.
  `compat.rs` uses whichever the installed Camel has. It also removed
  `camel_folder_get_unread_message_count()`; the folder summary's counts
  replace it.
- The Camel caches of 3.56 and 3.58+ are not compatible (`folders.db`
  changed). A cache written by 3.60 makes 3.56 log
  `camel_db_get_column_ident` criticals; deleting `~/.cache/salutations`
  fixes it.
- IMAPX's `camel_folder_transfer_messages_to_sync()` never fills
  `transferred_uids`, even with UIDPLUS. It adds the moved messages to the
  destination's summary from the server's COPYUID answer, so the window
  finds their new UIDs by comparing the summary before and after (by
  subject, sent date and sender) for undo.
- When an IMAPX account has a real Trash folder, syncing a folder moves
  its messages flagged `\Deleted` to Trash rather than expunging them.
  Permanent delete therefore moves messages to Trash first, then flags
  and expunges them there.
- Camel's folder search sees only messages in the folder's summary, which
  is empty for a folder never opened and stale for one not kept offline.
  Search therefore refreshes each folder in scope before its server
  search. IMAPX searches From, To, Cc and Subject in the summary and
  sends `body-contains` to the server as `SEARCH BODY` (cached bodies when
  offline).
- New-mail notifications use `org.freedesktop.Notifications` rather than
  GNotification, for the per-notification sound choice (`sound-name` or
  `suppress-sound`) and the sender's avatar (`image-data`). The avatar is
  drawn with cairo in AdwAvatar's colours, since AdwAvatar only renders
  inside a realized window. A message notifies when its INBOX UID is above
  the highest one seen before (saved in `notify-state.ini`), it is unread,
  and Salutations did not move it there itself.
- IMAPX's `camel_offline_store_dup_downsync_folders()` returns NULL, not
  an empty array, when no folder is set for offline use. The binding is
  hand-written to return an empty list.
- Some Camel calls return a boolean answer and a `GError`. gir turns those
  into `Result<(), Error>` and drops the answer.
  `camel_sasl_try_empty_password_sync()` is bound by hand;
  `camel_store_can_refresh_folder()` and
  `camel_network_service_can_reach_sync()` are left out until needed.
- `CamelFolder` and `ESourceMailAccount` carry Evolution's per-account
  mark-seen settings. Camel stores them and does nothing with them.
- IMAPX folder info carries a type only for INBOX: the special-use
  attributes (Sent, Drafts, Archive, Junk, Trash) are stripped.
  `camel_store_initial_setup_sync()` reports them; `Session::special_folders()`
  wraps it. Camel also adds virtual Trash and Junk folders unless asked
  for `NO_VIRTUAL`.
- `camel_folder_get_message_finish()` can return NULL without an error,
  so the binding returns `Option`.
- `CamelFolder::changed` is emitted from an idle on the session's main
  context, not from Camel's worker threads.
- `soup3` 0.9's `tld_get_base_domain()` reads libsoup's result after
  freeing the hostname it points into. `links::base_domain()` calls the C
  function directly.
- `camel_offline_store_prepare_for_offline()` downloads only messages a
  folder's summary already knows, so a folder never opened gets nothing.
  The window refreshes each synced folder before downloading.
- The 3.60 header declares `camel_offline_settings_set_limit_value()`
  with a `gboolean`, and gir follows it; the value is an integer and is
  set through the C function.
- Camel has no public call to drop one cached body. `offline::prune()`
  deletes the file itself: an IMAPX folder's data cache sits next to its
  state file, each body at `cur/<hash>/<safe uid>` with hash bits 5 to 10
  of `g_str_hash(uid)` (camel-data-cache.c). A test pins the layout; if it
  ever changes, the cost is a download, since a missing file is fetched
  again.
- The per-folder offline-sync state is in the folder's `cmeta` file under
  the cache directory, so clearing `~/.cache/salutations` also resets
  which folders are kept offline.
- Evolution's `EMailSession` and `EMailUISession` are not in EDS. Their
  account, OAuth2 and password logic is reimplemented in
  `salutations-core/src/session.rs` and `auth.rs`. A rejected password
  currently fails instead of prompting.

Milestone 1 passed against a GOA "IMAP and SMTP" account. The OAuth2
path has not run against a real account yet.

The app is tested in the GNOME 50 SDK (GTK 4.22, libadwaita 1.9,
WebKitGTK 2.54, EDS 3.60.2) on a virtual display, against a local
Dovecot server through a non-GOA EDS source. The EDS 3.56 path is tested
the same way with Debian trixie's 3.56.2 Camel, EDataServer and IMAPX
provider in place of the SDK's.
